# 模块说明模板与证据规则

模块文件默认放在项目根，与 `AGENTS.md` 平级；已有 `docs/` 布局则沿用。模板按实际行为裁剪，可选主题不适用时删除或用一句有依据的说明代替。

## 引用约定

- **标签路径从项目根起，链接目标从当前 Markdown 所在目录起**。根文件示例 `[src/service.go:L20-L42](src/service.go#L20-L42)`；`docs/` 内示例 `[src/service.go:L20-L42](../src/service.go#L20-L42)`。标签和目标须指向同一文件。
- 起止行都要打开当前源码核对。Go/Python 及启用 TypeScript 编译器的 JS/TS 声明范围来自 AST；降级/其他语言正则只提供声明行，不能把它当作完整函数范围。语句、配置或测试断言也可按真实行号引用。
- 字段引用优先用独立源码链接。若沿用 `` `Type.Field`(L21) `` 简写，同一表格行必须附所属文件的行号引用，避免同名类型串包。
- 每项确定行为需有对应源码/配置/测试证据。注释与实现冲突时说明差异，推断显式标为“推断/待核实”。imports 仅证明导入，未解析的候选路由、任务和入口不能当作已启用功能。
- API 只列有使用价值的公开入口；测试函数与 getter 等辅助实现可在定位确有价值时列出。不可仅凭正则索引的未知导出性认定为公共 API。
- 将长流程拆成几步并引用关键分支，而非用整个大文件的行号代替解释。细节围绕行为、约束和维护定位展开。

## 分层与证据绑定

大模块先拆职责：父说明保留整体流程和子模块索引，具体行为放入子说明；父子互链，文件在 `modules.json` 中只归属一次。父概览无直接源码时不必套用全部细节表格，仍说明整体能力、协作与验证范围。测试/生成代码单独说明，不用索引条目充当业务功能。

重要行为表或流程段可整体放入 `<!-- agentsmd:claim 唯一ID -->` 与 `<!-- agentsmd:endclaim -->` 之间；区块外仍可写导航和背景。对应 ledger 的 module/document、状态与证据角色须一致，格式见 [分析产物与校验](analysis-artifacts.md)。推断和待核实状态必须在可见内容中说明。记录阅读过的入口/实现与测试处置，不能用文件归属数量表示深读程度。

## 功能描述的粒度

“提供保存功能”不足以解释行为。若源码支持，可写为：“由 HTTP handler 接收记录，校验标识后调用存储接口；成功返回记录 ID，校验失败直接返回，存储错误向上层传递。”分别链接校验、存储调用和错误分支。只有读取到去重、事务或重试代码时才加入这些保证；这是写法示例，不是项目事实。
